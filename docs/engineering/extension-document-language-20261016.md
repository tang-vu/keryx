# Public-document language during extension research

An October 16 live diagnostic sent one anonymous Quick question through the
extension's existing chat endpoint with a zero source budget. The request ended
after 158.36 seconds with a completed evidence refusal, rather than a supported
answer. This establishes completion of that request, not the installed Edge
extension's identity or the cause of every reported wait.

The original Chrome popup documentation URL redirected to a Hindi translation.
A separate read-only VPS comparison using the reader's existing feed headers
redirected the same URL to a Latin American Spanish translation. With article
Accept types and `Accept-Language: en`, the same original URL stayed on its
English representation and included the popup closing statement. No model,
search or payment was invoked by that comparison.

Public article reads now explicitly negotiate HTML, text, Markdown and PDF with
an English default. Explicit language parameters in caller or publisher URLs
remain intact. This preference is not a guarantee of response language, nor a
translation or a rewrite of evidence. The actual final URL, extracted text and
content identity still define provenance. Feed requests retain their existing
negotiation. Redirect DNS/socket checks, HTTPS, content-type/byte/deadline bounds,
isolated extraction and evidence gates remain in force.

The shared hosted reader serves web, extension, API, remote MCP and bot research;
CLI, desktop and stdio MCP use the same reader when their existing execution
policy admits public research. No surface gains a signer, spend allowance,
retry, scheduler or account authority. Extension bytes and its independent
version are unchanged. Runtime delivery belongs to the existing deployment batch.

The live run also spent about 69 seconds between its web-discovery summary and
completed candidate discovery. Its precise cause remains unconfirmed. This
patch does not claim a latency improvement or a useful live answer after delivery.
