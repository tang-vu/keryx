# Evidence-bounded API integration notes

The API/platform specialist brief starts the original caller request with the
exact first line `Prepare an API integration note.`. Ordinary web/API/MCP/CLI
callers can use the same line. Quoted source material or added context cannot
select the format: the agent checks the original caller question.

The final note presents already accepted evidence as constraints/conditions,
exact excerpts, actual read scopes and missing topics. Implementation checks
are labelled proposals. It uses the existing answer Markdown, citations, receipts
and exports. The small answer renderer supports these headings and bullets.

This is a final presentation step. Synthesis, evidence qualification and creator
attribution run on the canonical grounded answer first. The projection does not
change the attribution input, citation marker set, reads, model calls, reservations,
source budgets, creator amounts or settlement authority. Existing confidence and
operational notices remain after the projection.

The note retains complete quoted conditions. It falls back to the original answer
when there are no qualified rows, more than 16 distinct evidence rows, more than
eight requested topics, over 12,000 output characters, or any mismatch with the
original citation marker set. Requested topics and excerpts cannot inject citation
controls or Markdown block structure. A section read remains a section read.

Private/bounded execution, procurement targets, paid-scholarly work, explicit answer
formats and explicit word/sentence/bullet limits keep their existing flows. The
projection supports the existing English, Vietnamese, Portuguese and Spanish
presentation languages.

Focused checks cover selection/qualification, marker equality, literal escaping,
size refusal, missing evidence and scope disclosure. The actual shared agent test
uses a real isolated section reader with synthetic provider judgments: ordinary
and note requests have identical attribution input, citation markers, read and
synthesis counts, zero source spending and a valid final receipt. Added context
cannot override a different original request. These spending-free fixtures do not
claim production model usefulness or complete API applicability.
