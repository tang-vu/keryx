# French ordinary answers and presentation

This source increment adds French to the existing finite ordinary-answer contract:
`en`, `vi`, `pt`, `es`, `fr`; `pt-BR` remains a request alias of `pt`. It is separate
from the partially translated, explicitly selected UI previews. Choosing a French
UI preview does not request a French answer or establish its language.

## Intent and original data

An explicit instruction in the unchanged original question, such as “Répondez en
français” or “Answer in French”, selects French for the admitted ordinary producer.
The parser remains bounded, with clause/quote/negation checks and last-positive
precedence. The ordinary shorthand “In English, …” can supersede a preceding French
directive; a numeric word limit cannot replace a language instruction. Existing
retained grammar is preserved. This is not a general French language detector.
The existing maximum-word projection remains English-only and finite sentence-note
formatting remains Spanish-only; French uses the existing safe short-bullet layout
or the complete target layout when compacting would lose evidence.

Authenticated bots may also pass their recipient-scoped, read-back-confirmed answer
preference as an internal structured option. An explicit supported instruction in
the original question wins. Help-only preferences are not migrated into answer
intent, and no instruction is appended to the original question.

Public API/MCP `language` and CLI/Desktop presentation preferences retain their
**labels-only** role. The new `fr` enum value does not enter generation input, signed
paid bodies, request hashes, query identity, funding or recovery. A caller can ask
for a French answer in the original question independently of its label preference.

## Generation, evidence and final language

French statement guidance runs before the existing separate evidence-review call.
That same bounded call can independently report a statement's actual `fr` language.
Missing, mixed, unsupported, duplicate, excluded or mutated observations withhold
sentence delivery. A requested language, a synthesis property or a serialized clone
does not provide review authority. Source/quote/support admission stays separate.

The ordinary renderer has French summary, excerpt-only, unavailable, evidence-gap,
compact/refusal and confidence copy. The API integration note and supplied-original
status use French labels while retaining every original target, URL, excerpt,
qualification, citation and machine field. French manual recovery and the same
observed PDF page/text scope retain extraction limits, exact-version checks and
the fact that OCR, images and figures were not interpreted. Recovery starts no
read, supplier call, purchase or automatic retry.

Only the existing observed ordinary partition admits the new French renderer.
Private, execution-limited package and teaching originals keep their prior path;
French intent does not enroll those producers. A final `keryx-answer-language-v1`
packet requires the selected renderer and every delivered reviewed sentence to
agree and binds exact final UTF-8 answer bytes. Stored and completed readers retain
closed schemas, query binding and strict canonical codes; request aliases and
`fr-FR` are not recorded-language evidence. No history is rewritten or backfilled.
Older readers may reject the new code and retain their honest UNKNOWN fallback;
the answer and paid body remain unchanged.

Additional early, funding, recency, supplied-original, recovery, special or changed
synthetic-demotion prose still prevents the narrow final language packet. A French
recovery heading does not qualify a whole answer. Original quoted spans use `und`;
canonical citation controls and English financial authority keep their own tags.

## Financial and operational boundaries

Source eligibility still comes from the existing admitted ledger, independently
of sentence-language filtering. The rendered answer remains an input to the
existing attribution call. Different language can therefore change model-assigned
weights; source acceptance does **not** promise identical live payouts across
languages. Fixed mock allocations can establish deterministic arithmetic and
unchanged eligibility/caps, not economic equivalence of live model behavior.

There is no new supplier call, allowance, source budget, signer, nonce, payout
authority, reservation, settlement state or retry. Source-owned payTo and integer
micro-USDC allocation remain authoritative. New French financial/funding/settlement
and pause wrappers retain canonical English copy. Payment-review and paid-retry
instructions remain English, including within French operational follow-up.
Email localizes navigation only; original financial prose, settled-only delivery,
recipient rotation, rate limits and unsubscribe identity keep their existing roles.
No mail, bot message, funding, purchase or production action is part of this work.

Machine-authored language copy and model language observation are not human
translation approval, factual verification or useful-answer acceptance. UI locale
activation and existing critical glossary review gates are unchanged.
