## Preference and catalogue behavior

browser preference, language negotiation, English. Account wins over browser
when both stored values are valid/offered. Disabled or unsupported stored values
do not suppress a valid browser value. The existing bounded negotiator retains
quality weights, zero-quality exclusions and script restrictions.

Authenticated preference responses carry the bounded actual Accept-Language
request header. Before account response, and for anonymous clients, negotiation
uses bounded `navigator.languages`, representing browser language settings.
This does **not** claim exact anonymous HTTP-header negotiation: doing that
without request-dependent public SSR needs a separately admitted public
negotiation endpoint. That original271 distinction remains open for ROOT review.

Browser keys contain version, origin, canonical network and account wallet (or

## Private account endpoint and storage capability

`GET/PUT /api/me/locale-preference` are interactive cookie-session operations.
Every handled response is private/no-store. Any Authorization header, including
an empty or malformed Bearer header, is refused before cookie fallback, session
or body access. PUT requires exact configured Origin and allowed Fetch Metadata.
GET with no Origin requires `Sec-Fetch-Site: same-origin`; any supplied Origin
must still match configuration. Host and forwarded headers confer no authority.
Both methods require expected-wallet and exact compiled locale-network headers.

`accountSessionContext` validates cookie claims before loading the selected DB
and checks the durable session. The current canonical account identity is its
server-derived lowercase wallet, also used by existing account/session APIs;
the session hash is only a rotation/race guard. A body owner is never accepted.
Locale body is at most 64 actual UTF-8 bytes, version 1, with exactly locale and
version fields; decoding/body reading is bounded by three seconds and follows
auth/capability admission. Responses are bounded to 8192 bytes in the client;
client transport/body reading has a five-second abort deadline.

The scalar is exactly `keryx-ui-locale-v1:<en|vi|zh-Hans>`, at most 32 characters.
The server key is `keryx:ui-locale:account:v1:<sha256>` over the bounded configured
origin, canonical network and server wallet namespace. It is independent of
financial, registry-indexer, pilot and public-profile namespaces. No schema,
adapter, allowlist, profile purpose or session policy is changed.

Only the existing installed **enrolled SQLite** facade is admitted: its current
read/write provenance guard and network must match. Existing reviewed generic
`getSyncState`/`setSyncState` methods support the scalar without adapter mutation.
Readonly write authority, unknown/ordinary/Supabase facades, failed provenance
or realm mismatch remain unavailable, with no backend fallback. The ordinary
SQLite and Supabase methods and enrolled inventories were studied as source.
Supabase's ordinary setter can discard its returned error; this candidate does
not treat generic method presence or environment variables as a safe capability.
Supporting another backend needs its separately reviewed safe port and evidence.

Corrupt retained values refuse. Session/DB/owner identity is rechecked before a
write and before publishing its result. Writes require exact readback; errors or
different readback report unavailable/unconfirmed. A logout after commit can
leave a written value while refusing the response; no rollback is claimed.
There has been **no actual DB call or cross-device persistence observation**.
