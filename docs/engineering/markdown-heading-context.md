# Literal code names as heading retrieval hints

When a requester names an HTML section with inline backticks, the evidence context
selector now treats that short literal name like its existing double-quoted,
curly-quoted and guillemet forms. Previously, a code-delimited name could retain
only a matching heading or an incidental keyword while losing its following
substantive paragraphs. The equivalent double-quoted request already retained
those paragraphs.

Matched one-line backtick runs supply names in request order, sharing the existing
four-name limit. Names retain the same 120-character plain-heading rules and the
existing 8192-character question prefix. Unmatched, multiline and oversized names,
fenced code and indented code provide no new code-name hint. This is a bounded
literal-name convention, not a general Markdown interpretation or execution layer;
the preexisting ordinary-quote path is unchanged.

Only matching observed HTML h1–h6 roles qualify. TOC text, styled labels, restored
layout JSON and non-HTML metadata do not create heading authority. Duplicate actual
headings remain ambiguous sampled hints. Existing fragment precedence, candidate
ceilings, the 2000-character source-context budget and reserved lexical room remain
in force. Selected passages and quote offsets bind to the exact extracted source.
No hint proves a complete section read, factual support or the presence of every
qualification.

Native fixtures exercise HTML extraction, context selection, exact quote options
and the unchanged evidence ledger. Controlled support estimates remain capped by
the existing gate; missing evidence, unavailable authorization, low support,
synthetic-demo provenance and incomplete quotes remain refused. Public references
remain ineligible for creator rewards. Fixtures use synthetic documents and
judgments, with no provider, search, source purchase or production action. They
establish the retrieval behavior, not live research usefulness, a translation
approval, factual entailment or a confidence improvement.
