# Prospective idea planning and saved failure reports

The single authorized YouTube homepage attempt on app0.27.80 stopped during planning. Its early report identifier returned 404 from both the page and public dispatch API. The exact provider proposal was not retained, and the generic refusal cannot distinguish `needs_refinement` from `invalid_output`; this change does not claim a proven provider-specific cause or a successful new live answer.

The planner previously told open-category requests to seek refinement when selecting candidates would narrow their scope. It also requires named comparison subjects to be exact spans of the caller's question. That combination is unsuitable for a request to propose and compare topic ideas without naming candidates. The prompt now explicitly uses the existing ordinary constraints/claims protocol for prospective idea comparisons: proposed ideas are bounded, nonexhaustive hypotheses; their factual grounds and limitations still require evidence. Every requested audience, language, age, source/version qualification and evidence/demand distinction must remain. The named-comparison parser, eight-target ceiling, explicit exhaustive-scope refusal, evidence review, citation rewards and payment admission are unchanged. Prompt guidance is not a guarantee that a live model will follow the protocol.

`POST /api/ask` now saves a genuine planning refusal through the same `saveQueryRun` publication boundary used for ordinary research. It only does so before discovery, before any payment boundary and while the request remains active. The saved original has empty targets/evidence/citations, zero source USDC, the original question and budget, actual available model counters, and closed `planningFailure` metadata: version, decompose stage, allowlisted reason, target ceiling, no automatic retry, and an observed output-token ceiling when available. Supplier text is never a diagnostic field. No `done` event, answer-completed activation or successful-research claim is emitted.

The early public/unlisted report identifier therefore resolves after a successful failure save. Private originals remain owner-gated. A failed save is reported honestly as `reportSaved:false`; it grants no retry. Anonymous private history claims retain their separate one-shot packet and same-document/clean-EOF checks. A saved failure can receive that existing claim, but its identifier grants no ownership, reading, funding or retry authority. Cancellation and later-stage errors do not fabricate a zero-spend planning record. Existing failed originals are not rewritten or replayed.

## Validation

- Regression baseline: six new failures and nine passes, natural exit 1/full EOF. Five failures demonstrated the missing persistence/claim behavior; one covered the missing prospective-idea prompt contract.
- Final focused coverage: 196 unique passing cases across nine files, including the real JSON engine with deterministic transport for the exact YouTube question, original SQLite comparison, named/exhaustive/oversized controls, real SQLite publication plus the actual permalink API, private/cross-owner reads, save failure, cancellation and one-shot claim boundaries. A fixture timestamp and an expectation for the existing `no-store` header were corrected; original failed captures remain retained.
- Scoped ESLint and whitespace checks passed. Required hosted type/build/domain checks remain merge gates; no full local suite or build was repeated.
- The existing offline 48-trial study was regenerated and checked with zero outbound attempts. Every trial field and canonical trial byte is identical; only the `json-chat-engine.ts` source hash changed. Corpus, scoring and boundaries were not changed.

All local transport responses and source bodies are controlled fixtures. No provider, model, search, original-question retry or payment call was made. The two live finite attempts remain consumed; this implementation does not renew their allowance or create another attempt.

## Supported surfaces

Web research uses the shared planner and now retains planning-failure reports. The dispatch API exposes only the closed diagnostic under the existing privacy reader. Repository CLI, OpenAI-compatible API and remote MCP share the planner correction; their existing terminal-refusal and persistence roles remain unchanged. Stdio MCP, desktop, browser extension and bots continue their existing hosted handoffs rather than acquiring a new local inference or payment path. The extension's listing role is unchanged.

The ten changed runtime/test paths are absent from all three retained distribution input closures: stdio 162 inputs, desktop helper 104 and desktop renderer 36. No dependency, package version, installer or publication input was changed. This is a source boundary audit, not a claim that an installed app or published artifact has been updated. ROOT owns final-source CI qualification, merge ordering, version allocation and the next combined deployment.
