## Immediate integration constraints

- `getDb()` at [lib/db/index.ts:12](../lib/db/index.ts#L12) now shares initialization and publishes only a ready adapter. It does not guard constructors, direct adapter methods, raw SQL helpers, or backend credentials. It selects Supabase from credential presence (`hasSupabase`, [lib/config.ts:295](../lib/config.ts#L295)); incomplete Supabase configuration silently selects the local SQLite store today. Expected backend and storage identity must become explicit and fail closed rather than inferred from available credentials.
- `SqliteAdapter` constructor opens/creates its path at [lib/db/sqlite-adapter.ts:378](../lib/db/sqlite-adapter.ts#L378), defaulting to `data/keryx.sqlite`. `init()` at line390 performs writable PRAGMAs, schema installation, column migrations, legacy counter removal, and cache migration. Guard identity before these operations and before methods on direct/read-only adapters; a read-only constructor is not an identity check. `KERYX_SQLITE_PATH` in backup tooling is not consumed by this constructor, so backup selection and application selection can currently diverge.
- `SupabaseAdapter` constructor at [lib/db/supabase-adapter.ts:110](../lib/db/supabase-adapter.ts#L110) uses `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; `init()` reads/migrates caches. Service-role access and helper RPCs need an independent database-side fence plus the client boundary. An application-only `getDb()` assertion does not protect a raw service-role client or migration tooling. Public SSR clients use publishable credentials and cookies; their auth scope is separate from service-role ledger access.
- `getPaymentGateway()` at [lib/payments/payment-gateway.ts:68](../lib/payments/payment-gateway.ts#L68) chooses forced offline before browser grants, then treasury real mode if a funder key exists, finally offline when no key exists. Real storage must refuse forced offline and absent-key treasury fallback; an authorized browser co-sign path can remain available without a treasury key. Offline storage must refuse real settlement, grant reservation/signing, and withdrawals while allowing explicitly simulated records only. Missing treasury keys must not silently change an enrolled real identity. This inventory does not introduce a generic network switch.
- `cacheEncryptionRequired()` at [lib/sources/content-cache.ts:13](../lib/sources/content-cache.ts#L13) independently depends on production/funder/forced-offline conditions. Mode fencing must cover cache migration and delivery, not just payment selection. Keep existing encryption keys and content receipt bindings intact; do not infer storage mode from key presence.
- Raw application store access in [lib/gateway/withdrawal-application-store.ts:10](../lib/gateway/withdrawal-application-store.ts#L10) reads withdrawal attestations; `withWithdrawalCashOutStore` at line27 opens writable application storage and records cash-out evidence. Current path/schema checks are not deployment identity checks. Both require an application-store guard before reads/writes. The mint relay journal is a different store and must not inherit application-store authority.

## Authority-relevant table groups

Treat the whole enrolled application store as identity-scoped. A financial-only table trigger list is insufficient: sources and cached content can change delivery/payee decisions; authentication tables can confer authority; restore/import/migration can replace state. The catalogue below lists every table declared in current `lib/db` SQLite schemas and SQL migrations. Grouping does not reduce fence coverage.

- Financial/settlement authority: `payment_events`, `withdrawals`, `browser_authorization_intents`, `session_grants`, `browser_journal_*`, `browser_signer_capacity`, `browser_retained_grants`, `creator_withdrawal_*`, private research payment/execution/creator/treasury/interruption tables, and A2A jobs/claims/resolutions. Preserve pending/exposed originals, signer spent capacity, epochs/nonces, idempotency keys, leases and all immutable barriers.
- Authentication and admission: `auth_challenges`, `web_sessions`, `api_keys`, `api_key_usage`, `users`, grant owner/session relationships, onramp reservations, rate limits and authorization claims. Reads matter as much as writes: accepting a grant/session/challenge from the wrong store crosses authority without inserting a payment.
- Payout/delivery/discovery: `sources`, source metadata, source items, offers, gap intents, notifications, sync state, public references and content cache. Registry payout authority and database fallback policy remain unchanged; storage identity does not authenticate a cached on-chain record.
- Private user/evidence state: query runs/memories, answer feedback, private results/history, activation/economics evidence and reasoning circuit state. Cross-mode reads can expose private content or contaminate evidence even when settlement is disabled.
- Migration and coordination state: identity/enrollment metadata when implemented, journal writer/control rows, backend schema/migration history and helper indexes/triggers/functions. Identity itself must be immutable to ordinary app connections. Administrative schema writers remain a separately trusted operator capability.

## SQLite connection capability proposal

A guard must be installed for every enrolled application connection, including raw withdrawal reporting/recovery connections. Validate exactly one supported immutable identity before configuration/migration/data access; require explicit expected identity and connection intent (`application`, `read-only recovery/report`, `migration`, or separately authorized enrollment). Do not obtain a capability by inserting a persistent row that another connection can reuse.

A connection-local, non-deterministic SQL function can expose the validated capability to persistent write triggers. Missing functions on unguarded raw connections cause writes to fail; false/mismatched capability also refuses. The callback must not read private data, mutate state, or be registered before validation. Cover insert/update/delete and test REPLACE, cascades, views, trigger-driven changes and cross-connection attempts. Existing SQLite schema installation and legacy migrations need a narrowly scoped checked migration capability; migration is not permission to enroll an existing store. Identity update/delete/schema replacement must not be an ordinary application capability.

Browser compatibility is mandatory: [sqliteJournalTransaction](../lib/db/sqlite-browser-journal.ts#L67) starts `BEGIN IMMEDIATE`, inserts `browser_journal_writer`, performs the operation, deletes that row and commits/rolls back. Its writer-row guard is an independent journal fence. Preserve it alongside the storage capability, original tuple/nonce/epoch checks, exact micro-USDC and retained capacity. Do not globally ban journal writer rows, activate the journal during enrollment, or replace journal exclusivity with a generic storage identity match.

Write triggers do not protect reads. Checked adapter methods and raw reader factories must refuse before returning authentication, grants, receipts, payout/cache/private state. `DatabaseSync.setAuthorizer` is available in the baseline Node24.12 API (added24.10); it can restrict connection operations, but runs during prepare/reprepare, so a prepared statement is not a reusable identity acceptance proof. Do not query the same connection inside its authorizer. Wrap execution/iterator progression or make immutable validated connection lifetime and identity-mutation prevention explicit, and test prepared-before-revocation behavior. Refuse unauthorized ATTACH/schema/extension/PRAGMA operations; keep capability unavailable to arbitrary SQL supplied by callers. See [version-pinned Node documentation](https://nodejs.org/download/release/v24.12.0/docs/api/sqlite.html#databasesetauthorizercallback). This is a proposed strategy, not an implementation or claim of hostile filesystem-owner protection.

The storage fence is an accidental/wrong-deployment and stale application prevention boundary under a trusted administrative owner. A local owner who can replace files/schema or register arbitrary native SQL functions, or a backend owner who retains unrestricted service-role/admin credentials, is outside a strong connection-capability claim. Document that residual scope rather than promising an ACL SQLite cannot provide.

## Proposed runtime manifest and integration API

Names and signatures below are proposed for implementation review, not existing operational controls. The shared leader API currently proposes `StorageIdentity`, `validateStorageIdentity`, `storageIdentityDigest` and `STORAGE_TESTNET_PROFILE_DIGEST`. Keep that pure pinned contract independent of secrets, manifest IO, backend clients and runtime key presence.

Introduce a dedicated server-only `lib/db/runtime-storage-config.ts` reader with one explicit `KERYX_STORAGE_MANIFEST` path. Require a canonical absolute existing regular file with no symlink ancestors, a small fixed byte bound (proposed 8 KiB), a fixed version and exact allowed keys. Return a validated frozen canonical copy. A canonical serialization requirement or duplicate-key-rejecting parser must prevent ambiguous JSON documents; fail closed on malformed/unknown fields, target/path replacement, unavailable files, and read errors. Redact paths/errors. Do not load any `.env` or adopt the identity found in the database.

```typescript
// Proposed nonsecret document; discriminated backend target is mandatory.
type StorageDeploymentManifest = {
  format: "keryx-storage-deployment-v1";
  identity: StorageIdentity;
  backend:
    | { kind: "sqlite"; databasePath: string }
    | { kind: "supabase"; url: string };
};
// Server-only resolver; validates manifest + target credential presence/match.
readRuntimeStorageDeployment(): Readonly<StorageDeploymentManifest>;
```

The SQLite target is a canonical absolute existing store; fresh provisioning is a separate explicit command/helper, not a constructor side effect. Recovery/report tools that select another file need an explicit manifest binding that selected target while retaining the intended original storage/deployment lineage; neither a CLI path nor the copied store's own marker supplies permission. Backup and restore need separate source/output intents rather than an implicit target override.

The Supabase target is one canonical HTTPS origin without credentials, path/query/fragment or alternate target adoption. `NEXT_PUBLIC_SUPABASE_URL` must exactly match it and the selected service-role credential must be present; a missing/partial pair refuses. A selected SQLite backend remains SQLite even when unrelated Supabase variables exist. No fallback to another backend follows an import/init/credential/identity failure. Local test transport exceptions must be explicit injected test fixtures, not a production HTTP escape hatch.

`getDb()` resolves the deployment once per initialization attempt and passes mandatory full identity: proposed `new SupabaseAdapter(expectedIdentity)` and `new SqliteAdapter(databasePath, { expectedIdentity, readOnly })`. Backend target assertions precede construction. Read-only direct adapters need the same expected identity before any method, and they must not call `init()`. The shared identity API remains leader-owned; Supabase helper/RPC changes stay PostgreSQL-owner-owned. No runtime integration layer can independently invent enrollment metadata or a profile digest.

`getPaymentGateway()` resolves explicit authority mode. A real manifest plus `KERYX_FORCE_OFFLINE=1` refuses; a real manifest with an authorized browser session/callback can choose the browser gateway without a treasury key; a real treasury request without a key refuses. An offline manifest selects explicit simulation and refuses browser/signing/real settlement regardless of available keys. `KERYX_FORCE_OFFLINE`, LLM availability, key presence, production NODE_ENV and credential presence never define identity. Content cache/source encryption policy, health/preflight labels, A2A worker/merchant availability and withdrawal admission must use the same validated mode. Independent testnet signature policy remains separate.

Do not import this filesystem reader into `lib/config.ts`: that shared module is imported by browser code such as `lib/hooks/use-session-grant.ts` and `lib/session/gateway-deposit.ts`. Any additions there must stay pure/client-safe. Node-only manifest validation belongs at server authority entrypoints; server code can consume the reader without exposing a private manifest or backend target to client bundles.

CI/build preparation explicitly provisions a fresh offline fixture store, a validated synthetic identity and its manifest in a new isolated temporary directory, then passes its manifest path to the child build. The helper refuses nonempty/existing store enrollment and never uses a production path or adopts a marker. Standard `npm run build` must invoke this isolated fresh offline fixture build, masking known signing/secret environment variables before Next can load dotenv. A separate deployment preflight may validate the selected production manifest/store read-only; the build never initializes, migrates or enrolls existing production storage. Do not hide missing manifests behind a build-phase constructor exemption or global Vitest bypass. Test fixtures should call a reviewed explicit provisioning helper and pass expected identities themselves; existing funded/crash/private-worker fixtures preserve their actual journal semantics.

Proposed runtime integration ownership after shared API agreement: new runtime manifest reader/tests; `lib/db/index.ts` and factory tests; payment-gateway/tests; content-cache and store-source-item mode policy/tests; raw withdrawal application-store helper/tests; direct economics/archive/funded-recovery/drill/backup/restore scripts; in-memory evaluation setup; fixture subprocess initialization; build fixture command/package/CI wiring; health/A2A merchant/research availability, worker/preflight/public-reference backend checks. SQLite adapters/pure identity/SQLite guard helpers remain leader-owned; Supabase adapter/helpers/migrations/PG tests remain PostgreSQL-owner-owned. Independent mint/Operator/browser namespaces are identified acceptance scopes, not silently migrated by this slice. Review exact touched-file ownership before coding.

## Build, CI, deployment and enrollment preparation

Current CI uses Node24 and secret-free builds ([ci.yml:20](../.github/workflows/ci.yml#L20)); production audit/build run near lines124/128. Static generation/server module imports must not create or enroll a store. Build/test preparation needs explicit synthetic identity inputs/stores and must not turn missing production settings into automatic offline enrollment. Tests already import direct adapters and raw SQLite; all legacy fixtures must adopt an explicit fresh-store capability. Keep `.mts` script checks explicit.

[redeploy-vps.sh:62](../scripts/redeploy-vps.sh#L62) drains private/withdrawal workers before source/dependency changes, but the old web build continues serving. Lines95-108 typecheck/build, restart the A2A worker and swap the web build; health rollback can restore the old build. This is release preparation, not storage enrollment. Identity cutover requires a separately authorized full writer pause (including the web app, cron reconcilers, seed/import/backup/migration tooling), known-good backups, validated manifests, and refusal-safe rollback. An older build without fences must not be restarted against an enrolled store. Existing stop/drain mechanisms remain necessary but do not alone prove all writers paused.

`backup-db.mts` accepts `KERYX_SQLITE_PATH`, reads/snapshots the main DB and handles encrypted/off-host artifacts; `restore-backup.ts` creates a new output store and checks integrity read-only. Neither currently checks enrollment lineage. Withdrawal backup/restore verifies a distinct policy/fingerprint; it must retain its own identity and signed originals. Do not run backup/enrollment from a Next build hook, reuse an intake digest as a full-store CAS fingerprint, or assume PR66 provenance intake authorizes enrollment.

Supabase migrations are operator SQL, not run by `getDb()`. Migration0069 restricts browser journal tables/RPCs and writer capabilities; later storage migration must compose with those grants and security-definer functions. An unrestricted service-role request must not infer expected identity from the store itself. Administrative credentials/migration role and runtime credentials require a reviewed rollout; parity stays open until real PostgreSQL tests demonstrate direct writes and every existing RPC fail closed.

## Implementation acceptance matrix

1. Exact match only: missing/partial/malformed/version/backend/deployment/store/profile/mode mismatches refuse before mkdir/create/PRAGMA/schema migration/cache reads or migration, and before returning any authority data. Constructor/direct method/raw helper and getDb paths are all exercised. Configuration absence on a real deployment cannot redirect to SQLite or offline.
2. Explicit legacy provenance: unknown funded or pending stores are not enrolled automatically; explicit private manifest binds complete snapshot/backup lineage separately from selected intake observations. Concurrent enrollment attempts have one immutable result; mismatched attempts refuse. No authority rows change during enrollment.
3. Connection-level enforcement: two live connections, unguarded raw writes, old binary/API paths, stale prepared statements, rollback/restart/restore, REPLACE/trigger/cascade, identity tampering/schema reset and privileged migration paths. Read-only reports/recovery verify identity without init. Raw authority reads through supported tooling refuse before values escape.
4. Mode boundaries: enrolled real storage with force-offline, missing funder key, browser grant, server merchant/worker, cache encryption and withdrawal paths; offline storage rejects real claims/grants/signatures/settlement/withdrawals. Simulated historical rows remain historical in real stores; pending real rows never become simulated or failed from missing evidence.
5. Browser journal nonregression: activated/inactive stores retain control, exact nonce/epoch/payee/payer/caps/spent/phase/immutable original/signature metadata across fence installation, concurrent admission, exposure, uncertain writes and recovery. Independent worker testnet pins and browser funded derivation remain unchanged.
6. Supabase parity: actual PostgreSQL service-role, direct insert/update/delete/select/RPC, auth/publishable RLS and migration role boundaries, cache startup, serialized private envelopes and journal transactions. A SQLite-only implementation cannot close M2.
7. Separate journal boundaries: reject an application database passed as mint journal or vice versa, wrong relayer/policy/store/restore lineage, unknown Operator workspace and browser import/mode mismatches. Do not claim these stores covered by the main adapter fence until independent acceptance exists.
8. Release preparation: fresh isolated CI build/tests without production manifests/data; exact production manifest checks before worker/web authority starts; complete paused-writer enrollment rehearsal and fenced rollback. No mainnet switch, keys, funding or deploy is authorized by this inventory.
