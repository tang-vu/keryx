# SQLite storage identity candidate

Internal implementation review, 2026-10-01. This candidate supplies explicit fresh provisioning and conservative reviewed legacy enrollment; it does not authorize production enrollment, mainnet activation, or M2 closure. Runtime caller compatibility, PostgreSQL parity, owner evidence, backup/restore and rollback acceptance remain release gates.

`StorageIdentity` pins the exact deployment UUID, store UUID, Arc testnet profile digest, explicit real/offline authority mode, enrollment UUID/time and owner provenance-document digest. No environment-derived identity, network selector, missing-marker fallback or reset is accepted. `createSqliteStorage(canonicalAbsolutePath, identity)` exclusively creates a new empty file. Existing files require `inspectSqliteEnrollment(path, identity)` followed by `enrollSqliteStorage(path, identity, reviewedEvidence)`. These asynchronous APIs perform native inspection in a bounded child; provisioning is separate from normal adapter initialization.

Reviewed evidence must match the exact held target, expected identity, schema and complete typed logical snapshot, and explicitly attest every reported unknown class. The snapshot includes every table, every payload, exact INTEGER/BLOB/TEXT/REAL tags, hidden row identifiers where applicable, and WITHOUT ROWID tables. Invalid UTF-8 TEXT, views, virtual/generated columns, unsupported tables or oversized coverage are refused. This full snapshot comparison is stronger than the selected-authority intake digest described in [provenance inspection](storage-provenance-inspection.md); neither digest proves historical payment origin or authorizes enrollment by itself.

Nonempty funded, grant, browser authorization, authentication, withdrawal and private financial authority tables are conservatively refused when legacy provenance is unresolved. An owner attestation cannot make those rows spendable. Existing rows and nonces, epochs, caps, holds and journal activation remain untouched on refusal. Supported metadata and explicitly simulated historical payments can be reviewed without silently relabeling their origin. Real stores retain historical simulations but reject new simulated financial writes; offline stores reject real payment writes, funded grants and signing/withdrawal authority, including journal activation by INSERT or UPDATE. New top-level payment, withdrawal and browser authorization profile fields must match the pinned testnet profile. Existing journal tuple and protocol validation remains necessary for serialized authority.

Enrollment installs the immutable marker and all inventory-table write triggers in one IMMEDIATE transaction. An exact repeat verifies the complete identity and exact trigger bodies before acknowledging; it never repairs a damaged fence. Competing enrollments serialize. A child deadline may occur after COMMIT and therefore returns an uncertain acknowledgment: inspect or repeat the same identity; never generate a replacement enrollment to recover acknowledgment. Fresh creation failures can leave an unlabelled partial file, which is refused rather than automatically overwritten.

Exclusive creation retains its original file descriptor through comparison with the admitted pathname descriptor and the operation lifetime. An ordinary empty-file replacement is refused rather than adopted. Reviewed inspection comparison uses sorted structured JSON fields; reordering object keys does not require a new enrollment identity.

`backupVerifiedSqliteStorage(source, expectedIdentity, freshOutput)` is a separate readonly snapshot capability. It holds an admitted source read transaction, copies with the native SQLite backup API to exclusively created output, and checks the copied identity, exact fences, integrity and full logical snapshot. This preserves hidden row identifiers as well as grants/nonces/caps and journal rows. Its lineage receipt explicitly states `signingResumeAuthorized: false`: a copied store is not permission to run a second signer deployment. Output cannot overwrite an existing file. Deadline or acknowledgment failures retain uncertain output for readonly inspection; do not overwrite, relabel or automatically adopt it. Runtime/operator backup and restore wiring and recovery acceptance are separate gates.

`new SqliteAdapter(path, { expectedIdentity })` validates the held file, marker and fences before any initialization PRAGMA, schema migration, cache access or authority read. Writable adapters require `await init()`; admitted readonly adapters provide reports without initialization or cache migration. All public operations recheck identity and filesystem binding, and schema changes force fence verification. WAL and connection PRAGMAs occur after identity admission but outside the schema transaction and are not rolled back. Schema, fence installation and cache migration use the initialization transaction and cache savepoint.

`openVerifiedSqliteStorage(path, identity, { readOnly? })` is narrow trusted application SQL access. Each prepared statement execution and iterator advancement rechecks the binding. Its authorizer denies schema changes, ATTACH/DETACH and extension loading; it requires Node SQLite authorizer support (Node 24.10 or later, exercised on 24.12). Connection-local capability functions allow compatible writes while old raw writers cannot satisfy the persisted triggers. Existing browser writer-row guards remain additional protections. SQLite cannot prevent a malicious filesystem/database owner from rewriting the entire file or defining its own functions; authority reads must use admitted application entrypoints, not arbitrary raw SQL.

Inspection limits are 64 MiB main file, 100,000 rows, 512 schema objects, 128 columns, 2 MiB fields, 128 MiB raw observed bytes and 32 MiB encoded rows/schema, with a 128 MiB V8 heap ceiling and independent 15-second parent deadline. These bound accepted work and JS encoding, not every native SQLite allocation. Process termination leaves SQLite transaction rollback/recovery responsible for uncommitted writes. Readonly WAL opens may affect coordination sidecars. Held-descriptor checks before and after pathname opening detect ordinary replacement; Node SQLite still opens by filename, so hostile swap-and-restore cannot be eliminated. Protected trusted local storage remains required.

Focused synthetic tests cover malformed UTF-8 refusal, typed/unselected payload snapshot changes, stale evidence, concurrent exact enrollment, actual writer-process termination before enrollment COMMIT, refusal preservation, damaged marker guards, old raw writers, compatible guarded writes, iterator cleanup and mode/profile mutations. Existing browser journal crash/cap/nonce/epoch tests pass using explicit synthetic real-mode identities and fixture encryption keys. No production/private store or funded operation was used for this candidate evidence.
